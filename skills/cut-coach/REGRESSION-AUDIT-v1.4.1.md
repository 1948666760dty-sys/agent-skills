# duty-NRV / Cut Coach v1.4.1 — Conflict Regression Audit

日期：2026-09-22

## 背景

v1.4.0 首次上传后做 post-write 审计，发现旧章节仍残留与新 Mobile First 规则冲突的要求，因此立即发布 v1.4.1 修复。

## 本轮发现并修复

1. PRE_EAT 路由旧规则要求“整体总表 + 分类明细”，与 v1.4.0 的“窄屏进度卡、不自动展开全部餐次”冲突。
2. “今晚推荐吃什么”专门回归仍要求分类明细，造成同一路由两套输出规则。
3. 运动章节仍出现“v1.3 默认规则”和 duty-NAV 热量目标旧称。
4. 估算章节仍把 duty-NAV 作为用户语义参考。
5. E 路由中“NRV 默认指 duty-NRV Skill”的措辞可能让 NRV 重新产生双义。
6. 成功标准仍要求“整体总表 + 分类明细表”，与窄屏方案冲突。
7. 官方 NRV 禁止规则使用“重新启用”措辞，可能被误解成长期切换状态。

## 必须满足的静态检查

- version = 1.4.1
- PRE_EAT 默认 = 个人 NRV 进度卡 + 缺口 + 推荐
- PRE_EAT 不默认展开所有餐次
- “今晚推荐吃什么”与通用 PRE_EAT 使用同一 Mobile First 规则
- NRV 默认 = 个人 NRV
- duty-NAV 只作为历史兼容别名
- 运动不自动改变个人 NRV 热量目标
- 默认核心 5 项保持不变
- 默认个人目标保持 2100 / 120 / 220 / 60 / 30
- 官方 NRV 仅在当前请求明确点名时显示
- REPORT = 今日总计 + 个人 NRV 进度 + 窄屏餐次列表
- LOGGED A 模式 = 本餐 + 今日累计 + 个人 NRV + 缺口 + 下一步
- 去重/幂等规则保留
- >100% 图形封顶、文字保留实际百分比
- 视觉估算百分比使用 ≈/约并保留合理范围

## 冲突回归场景

1. “晚上推荐吃什么”且今天已有两餐 → 进度卡 + 缺口 + 推荐，不自动刷两餐宽表。
2. “今晚吃啥” → 同上。
3. “完整列一下今天再推荐晚饭” → 允许展开全部餐次，但使用窄屏列表。
4. “今日” → REPORT，不是 PRE_EAT。
5. “NRV 呢” → 个人 NRV，同时触发 Cut Coach。
6. “官方 NRV 呢” → 官方 NRV，仅当前请求显示，不修改个人默认。
7. “明天也按官方 NRV”若未明确修改个人目标 → 不应自动把官方 NRV 设为新个人目标。
8. 16:42 主餐未标餐次 → 不自动判为晚餐。
9. 同一餐问“为什么热量高” → 不重复记账。
10. 同一餐剩饭修正 → 覆盖原记录。
11. LOGGED 后只给本餐 → FAIL。
12. LOGGED 后没有今日个人 NRV → FAIL。
13. PRE_EAT 自动展开 5～8 列宽表 → FAIL。
14. REPORT 自动使用宽横表 → FAIL。
15. 108% 画出超过 10 格 → FAIL。
16. 108% 图形 10 格 + 文字 108% → PASS。
17. 食堂照片估算写 86% 不带约/≈ → FAIL。
18. 食堂照片估算写 ≈86% 并说明合理范围 → PASS。
19. 运动 700 kcal 自动把 2100 目标改成 2800 → FAIL。
20. 运动记录存在但个人 NRV 仍用 2100 目标 → PASS。

## 继承

v1.4.0 的 60 条回归场景全部继续有效；本文件额外覆盖 v1.4.0 上传后发现的内部一致性问题。

## 结论

本轮为规格级/静态冲突审计。它验证 canonical 文本不存在上述已知冲突，但不等同于独立模型逐条 live execution。
